# 训练侧对接说明（LLaMA-Factory → 边训边评）

给训练侧同学看的。读完这一份就够了，不需要看仓库里其他文档。

---

## 一、30 秒版：你要做什么

训练途中每保存一个 checkpoint，往一个**固定的共享目录**里写两个文件：一个 JSON、一个空的 `.done`。
训练结束时再写一次。

就这些。**不需要调接口、不需要等返回、不需要装任何依赖、不影响训练速度、评估失败也不会影响训练。**

评估侧有个常驻进程一直在扫那个目录，看到 `.done` 就去读 JSON，拿到 checkpoint 路径后自己去评估机上跑，
出分数、出趋势图、出下一轮的数据配比建议。整个过程跟训练进程完全解耦。

```
你（训练机）                          我（评估机，8×80G，独立）
    │
    │ 存完 checkpoint-600
    ├──► 写 step-600.json
    ├──► 写 step-600.json.done ──────►  扫到 .done
    │                                   ├─ 读 JSON 拿到 checkpoint 路径
    │  （训练继续，不等待）               ├─ 跑领域评估 + 通用评估
    │                                   └─ 出分数 → 趋势表 → 报告
    ▼
  训练结束
    ├──► 写 finished.json
    └──► 写 finished.json.done ──────►  跑最终全量评估 + 出最终报告
```

## 二、先确认三件事（需要你回话）

| # | 要确认的 | 我这边的默认值 | 说明 |
|---|---------|--------------|------|
| **1** | 信号目录放哪 | `/mnt/si003010kcx0/mmdata/mmcode/trainspace/eval_signals/` | 见下面"为什么必须固定" |
| **2** | `run_id` 由谁生成、怎么生成 | `<模型简称>_<数据版本>_<日期>_<时分>` | 规则见 §4 |
| **3** | `mix_strategy` 是不是 `concat` | 是（LLaMA-Factory 默认值） | 如果你们用 interleave，**现在就要说**，见 §6 |

### 为什么信号目录必须固定

评估侧是一个常驻进程，它需要一个固定的地方去扫。如果信号目录跟着每次训练的 `output` 变，
就成了"我不知道该去哪找信号"的鸡生蛋问题。

所以把两件事拆开：

| | 固定还是动态 |
|---|---|
| **信号目录** | **固定**，双方约定死 |
| **checkpoint 路径** | 动态，你在 JSON 的 `checkpoint_path` 字段里传给我 |

`output` 每次换地方完全没问题，走字段传就行。

## 三、怎么写这两个文件

```
<signal_dir>/<run_id>/step-<step>.json        ← 先写
<signal_dir>/<run_id>/step-<step>.json.done   ← 后写，空文件
<signal_dir>/<run_id>/finished.json           ← 训练结束时
<signal_dir>/<run_id>/finished.json.done
```

**顺序是硬要求**：

```
checkpoint 目录完全写完  →  原子写 .json  →  fsync  →  写 .done
```

评估侧只扫 `*.done`，看到才去读同名的 `.json`。

### 为什么要多一个 .done 文件

LLaMA-Factory 保存 checkpoint 是多个文件陆续写入的。如果评估侧靠"目录出现了"或
"mtime 变了"来判断保存完成，就会读到写了一半的权重目录。

最坑的是**这种情况加载不报错**——transformers 能把残缺的 safetensors 加载起来，
跑出一堆看着正常但完全错误的分数。等发现的时候，趋势图上已经有一段假数据了，
而且没有任何日志能反推出问题在哪。

`.done` 是你在"全部写完之后"给出的明确信号，成本是一行代码，挡掉的是最难排查的一类事故。

## 四、`run_id` 怎么生成

```
<模型简称>_<数据版本>_<YYYYMMDD>_<HHMM>

例：qwen3vl8b_zbv3_20260908_1430
正则：^[a-z0-9][a-z0-9_]{2,63}$
```

三条约束：

1. **一次训练内固定不变**，中途不能改
2. **断点续训沿用同一个** —— 那是同一次训练的延续，趋势曲线要连成一条
3. **不同训练不能重复** —— 日期时间后缀负责这一点

`run_id` 是趋势表的分组主键。重复了会把两次训练的曲线混成一条，图就废了。

建议做法：在启动脚本里生成一次，导成环境变量 `EVAL_RUN_ID`，全程用它。
续训时手动传上次的值进去。

## 五、`checkpoint_saved` 字段详解

**下面出现的字段全部必填，没有可选项。缺任何一个我直接判失败并告诉你缺哪个。**
多余的字段我会忽略，不报错。

```jsonc
{
  "schema_version": "1.0",
  // 协议版本，固定 "1.0"。以后要改字段就升版本号。
  // 作用是防止协议悄悄漂移：你改了含义没告诉我，我还按老规则解析，
  // 出来的分数是错的但不会报错。

  "event": "checkpoint_saved",
  // 事件类型。两类信号丢在同一个目录里，靠它区分走哪条处理逻辑。

  "request_id": "qwen3vl8b_zbv3_20260908_1430__step600",
  // 幂等键，格式固定 <run_id>__step<step>。
  // 集群重启、脚本重跑都会重复投递，我按它去重——已经评过且成功的直接跳过，
  // 不会浪费机时评第二遍。

  "run_id": "qwen3vl8b_zbv3_20260908_1430",
  // 一次训练的唯一 ID，趋势表的分组主键。规则见 §4。

  "step": 600,
  // 全局训练步数，趋势图的横轴。

  "epoch": 1.5,
  // 训到第几轮，小数。两个用处：报告的第二横轴；
  // 定位训崩的位置时能说"第 2.4 轮开始掉的"，比只说 step 1200 直观。

  "saved_at": "2026-09-08T12:00:00+08:00",
  // 保存时间，RFC3339 带时区。只用来判超时（最后一个信号 6 小时没动静
  // 我就认为训练中断了）。不用来排序——两台机器时钟可能不同步，排序一律用 step。

  "checkpoint_path": "/mnt/si003010kcx0/mmdata/mmcode/trainspace/output/zb_v3/checkpoint-600",
  // 权重目录绝对路径，评估机要能读到。这就是那个"动态的"东西。

  "base_model_path": "/mnt/si003010kcx0/mmdata/mmcode/trainspace/model/Qwen3-VL-8B-Instruct",
  // 训练起点权重。所有"涨了多少/掉了多少"的对照基准都是它。
  // 没有它我只能给绝对分，说不出"比训练前好了 8.4 分"。

  "is_final": false,
  // 是不是最后一个 checkpoint。true 时我无视节流规则必评，且直接进全量评估。

  "train_meta": {
    "stage": "sft",
    // 训练阶段，报告归档用。

    "finetuning_type": "full",
    // full / lora。我拿它跟 checkpoint 实际形态交叉校验——
    // 声明 full 但目录里只有 adapter 文件，我直接判失败，而不是自己猜要不要 merge。

    "mix_strategy": "concat",
    // 数据混合策略，必须是 "concat"（LLaMA-Factory 默认值）。原因见 §6。

    "datasets": [
      { "name": "zb_equip", "samples": 12000 },
      { "name": "books",    "samples": 3000  },
      { "name": "general_mix", "samples": 4500 }
    ]
    // 各训练数据集的名字 + 实际参训条数。这是"下一轮数据配比建议"的基准：
    // 我要输出 "books: 3000 → 4000"，没有当前的 3000 就写不出目标的 4000。
    // 条数口径见 §6。
  }
}
```

去掉注释就是 `checkpoint_saved.example.json`，可以直接抄。

## 六、`samples` 条数口径 + 一个硬要求

### 条数怎么填

统一口径一句话：**这次训练实际喂进去多少条**，不是数据文件里有多少条。

| 你的训练配置 | `samples` 填什么 |
|---|---|
| 设了 `max_samples: N` | `min(N, 该数据集文件实际行数)` |
| 没设 `max_samples`（全量） | 该数据集文件实际行数 |

### 硬要求：`mix_strategy` 必须是 `concat`

用 `interleave_under` / `interleave_over` 的话，各数据集实际被采样多少条是由
`interleave_probs` 和总步数一起决定的，**"实际参训条数"这个概念根本不成立**，
我输出的 `books: 3000 → 4000` 也就无法落地。

**如果你们确实必须用 interleave，现在就说。** 我把配比建议的单位换成 `interleave_probs`，
信号里 `samples` 换成 `prob`，规则表同步改。

**二选一，不能两种都支持**——两种单位混在同一张趋势表里，历史数据会全部失去可比性。

## 七、`run_finished` 字段

训练结束时写一次。**崩了也要写**——我用已经积累的趋势数据出报告，只是不跑最后那次
十小时的全量评估。

```jsonc
{
  "schema_version": "1.0",
  "event": "run_finished",
  "request_id": "qwen3vl8b_zbv3_20260908_1430__finished",
  // 格式 <run_id>__finished

  "run_id": "qwen3vl8b_zbv3_20260908_1430",

  "status": "completed",
  // completed / failed / interrupted，三选一

  "final_step": 2000,
  "final_checkpoint_path": "/mnt/.../output/zb_v3/checkpoint-2000",
  // 最终权重，最后一次全量评估的对象

  "finished_at": "2026-09-08T20:31:00+08:00"
}
```

## 八、参考实现（可直接抄）

```python
import json, os, tempfile, datetime
from transformers import TrainerCallback

SIGNAL_DIR = os.environ["EVAL_SIGNAL_DIR"]      # 固定的共享目录
RUN_ID     = os.environ["EVAL_RUN_ID"]          # 一次训练固定不变
DATASETS   = json.loads(os.environ["EVAL_TRAIN_DATASETS"])
# 例：[{"name":"zb_equip","samples":12000},{"name":"books","samples":3000}]


def _emit(payload, filename):
    d = os.path.join(SIGNAL_DIR, RUN_ID)
    os.makedirs(d, exist_ok=True)
    path = os.path.join(d, filename)
    # 原子写 json，再写 .done。顺序不能反。
    fd, tmp = tempfile.mkstemp(dir=d)
    with os.fdopen(fd, "w", encoding="utf-8") as f:
        json.dump(payload, f, ensure_ascii=False, indent=2)
        f.flush()
        os.fsync(f.fileno())
    os.replace(tmp, path)
    open(path + ".done", "w").close()


def _now():
    return datetime.datetime.now().astimezone().isoformat(timespec="seconds")


class EvalSignalCallback(TrainerCallback):
    def on_save(self, args, state, control, **kwargs):
        if not state.is_world_process_zero:   # 这行不能删，见下
            return control
        step = state.global_step
        _emit({
            "schema_version": "1.0",
            "event": "checkpoint_saved",
            "request_id": f"{RUN_ID}__step{step}",
            "run_id": RUN_ID,
            "step": step,
            "epoch": round(float(state.epoch or 0), 4),
            "saved_at": _now(),
            "checkpoint_path": os.path.abspath(
                os.path.join(args.output_dir, f"checkpoint-{step}")),
            "base_model_path": os.environ["EVAL_BASE_MODEL_PATH"],
            "is_final": bool(state.max_steps and step >= state.max_steps),
            "train_meta": {
                "stage": os.environ.get("EVAL_STAGE", "sft"),
                "finetuning_type": os.environ.get("EVAL_FT_TYPE", "full"),
                "mix_strategy": "concat",
                "datasets": DATASETS,
            },
        }, f"step-{step}.json")
        return control

    def on_train_end(self, args, state, control, **kwargs):
        if not state.is_world_process_zero:
            return control
        step = state.global_step
        _emit({
            "schema_version": "1.0",
            "event": "run_finished",
            "request_id": f"{RUN_ID}__finished",
            "run_id": RUN_ID,
            "status": "completed",
            "final_step": step,
            "final_checkpoint_path": os.path.abspath(
                os.path.join(args.output_dir, f"checkpoint-{step}")),
            "finished_at": _now(),
        }, "finished.json")
        return control
```

两个注意点：

- **`state.is_world_process_zero` 那行不能删。** 集群多进程会每个 rank 都写一遍，
  产生重复文件和竞争写入。
- **`on_save` 的时机是对的。** transformers 里 `on_save` 回调是在 `_save_checkpoint`
  返回之后触发的，此时权重已经落盘。

挂载方式你们比我熟——LLaMA-Factory 是在 workflow 里往 `callbacks` 列表加。

## 九、你要遵守的三条硬约束

| # | 约束 | 不遵守会怎样 |
|---|------|------------|
| **1** | `.done` 必须在 checkpoint 完全写完之后才写 | 评估读到残缺权重，跑出错误分数且不报错，趋势图混入假数据 |
| **2** | **`save_total_limit` 不设，或设得足够大**（不要开轮转） | 评估有排队和节流，checkpoint 可能保存后一段时间才轮到评。期间被轮转删掉，这个点就永久缺失，报出来的错还是"路径不存在"，容易被误判成路径配错 |
| **3** | `run_id` 一次训练内不变，续训沿用，不同训练不重复 | 趋势曲线断裂或两次训练混成一条 |

第 2 条你们那边存储是充足的，直接关掉轮转就行。

## 十、自测：写完自己验，不用来回问

仓库里有个校验脚本，**纯标准库、不用装任何依赖**：

```bash
# 验单个文件
python3 contracts/validate_signal.py <signal_dir>/<run_id>/step-600.json

# 验整个信号目录（一次训练写出来的全部信号）
python3 contracts/validate_signal.py --dir <signal_dir>/<run_id>
```

它会检查字段齐不齐、类型对不对、`request_id` 格式跟 `run_id`/`step` 对不对得上、
`.done` 有没有写、`mix_strategy` 是不是 `concat`、条数是不是正整数等等，
错在哪一行说得很具体。

**建议流程**：先手工造一个信号文件跑一遍校验，通过了再接进 Callback，
接完让它空跑一次训练（`max_steps` 设小一点，比如 20 步存一次存三次），
用 `--dir` 把整个目录验一遍。全绿了再告诉我，我这边就能接上。

## 十一、常见错误对照

| 现象 | 原因 | 怎么改 |
|---|---|---|
| 校验报 `request_id 与 run_id/step 不一致` | `request_id` 手拼错了 | 用 `f"{RUN_ID}__step{step}"` 拼，别手写 |
| 校验报 `缺少 .done` | 只写了 json | `.done` 是空文件，`open(path+".done","w").close()` |
| 同一个 step 出现多份信号 | 多进程都在写 | 加 `state.is_world_process_zero` 判断 |
| 评估侧报 `checkpoint 已不存在` | `save_total_limit` 把它轮转删了 | 关掉轮转，见 §9 约束 2 |
| 评估侧报 `finetuning_type 与实际不符` | 声明 full 但存的是 adapter | 确认训练配置，或把字段改成 `lora`（那样需要先 merge，另说） |
| 趋势图两次训练混在一起 | `run_id` 重复了 | 加日期时分后缀 |

## 十二、FAQ

**Q：写这两个文件会不会拖慢训练？**
A：两个小文件的写入，毫秒级。而且只在保存 checkpoint 的时候写，本来就是 IO 密集的时刻。

**Q：评估挂了会不会影响我训练？**
A：不会。完全解耦，评估侧不向训练侧回传任何信号，也不做自动早停。评估崩了、评估机断电、
评估排队排到天亮，训练该怎么跑还怎么跑。

**Q：训练崩了没发 `run_finished` 怎么办？**
A：评估侧有超时兜底——最后一个 checkpoint 信号后 6 小时没有新信号，自动按
`interrupted` 处理并出报告。但能主动发还是发一下，报告里的结束状态会更准。

**Q：我一小时存一个和二十步存一个，对你有区别吗？**
A：有。评估侧有 30 分钟节流：间隔内到达的多个 checkpoint 只评最新的那个，其余记为跳过
（`is_final=true` 的除外，必评）。所以存得特别密的话，趋势图上的点会比 checkpoint 少，
这是设计如此，不是丢数据。

**Q：我能不能自己触发一次评估？**
A：能。手工往信号目录里写一份信号文件就行，跟训练自动写的没有区别。

**Q：评估结果我在哪看？**
A：评估侧会写趋势表和 HTML 报告，路径确定后同步给你。你不需要读任何评估产物，
这个协议是单向的。
