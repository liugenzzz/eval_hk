# 目标检测评估：跑通流程

分六阶段，**每一阶段都比上一阶段贵**，前一阶段没过就别进下一阶段。这样排的理由很实际：整套跑完是两个模型 × 十一个数据集 + 裁判调用，几个小时起步；路径写错、`kind` 拼错、裁判服务没起这类问题，要在第 10 秒发现，不是第 3 小时。

口径、指标定义、报表怎么读见 [../目标检测评估.md](../目标检测评估.md)，这份只讲**怎么跑**。

---

## 前提：手上要有这几样

| 东西 | 说明 |
|---|---|
| `test.jsonl` | 构建端产出的评估集。直接读，不用转格式 |
| 图片目录 | 和 `test.jsonl` 里 `images` 字段对得上 |
| `classes.yaml` | 构建端的类别表。**不配 E 组主指标会偏高**（见坑 ①） |
| `labels/` | YOLO 标注目录。配了 D 组的 CHAIR 幻觉才有数 |
| 构建端的 `prompts/describe/` | D 组范围合规的词表直接读它，不重写 |
| checkpoint | `base`（原始 Qwen3-VL-8B-Instruct）和 `sft` |
| 裁判服务 | 只有 D 组描述要，前四个阶段用不上 |

```bash
cp det.example.json det.json      # PowerShell: Copy-Item det.example.json det.json
```

`det.json` 顶层 `dataset_defaults` 里那四条路径改成评估机上的真实路径 —— **只改这一处**，十一个数据集自动都拿到：

```json
"dataset_defaults": {
  "image_root":          "/data/eval/images",
  "classes_yaml":        "/data/eval/classes.yaml",
  "labels_dir":          "/data/eval/labels",
  "describe_prompt_dir": "/data/builder/prompts/describe"
}
```

再改三处：`tsv_dir`（`test.jsonl` 所在目录）、`models[].model_path`（两个 checkpoint）、`infer.training`（照抄 LLaMAFactory 训练配置里的像素面积，见坑 ②）。

## 阶段 0 · 配置自检（10 秒，不用 GPU 不用裁判）

```bash
python -c "
from eval_tool.config import load_pipeline_config
from eval_tool.run_eval import _scoring_plan
c = load_pipeline_config('det.json')
print('数据集   ', len(c.datasets), '启用', len(c.enabled_datasets))
print('模型     ', [m.name for m in c.models])
print('交叉裁判 ', [(n, s.model) for n, s in c.cross_check_judges])
_scoring_plan(c.to_eval_config())
print('OK')
"
```

`_scoring_plan` 是关键那一行：它把每个数据集的 `kind` 解析成打分器，**拼错在这里就报错**，不会等你跑掉三小时推理才发现：

```
UnknownKindError: 未知的数据集 kind：'grounding_sngle'。已实现：choice, counting,
describe, exist_negative, grounding_multi, grounding_single, inventory, judge_text,
object_ident, perturbation, short_answer
```

**过关标准**：打印出 `OK`，且路径、模型名、像素面积都对。

---

## 阶段 1 · 20 条冒烟（几分钟，不用裁判）

先只跑**两个纯代码打分的数据集**、**只跑 sft**、**每个数据集只推 20 条**。这一步要证明的只有一件事：`test.jsonl → 推理 → 评估 → 报表` 这条管道是通的。

`det.json` 临时改两处：

```json
"enabled_datasets": ["ground_box", "region_identify"],
"infer": { "limit": 20, ... }
```

```bash
python -m eval_tool infer --config det.json --models sft
python -m eval_tool eval  --config det.json --models sft
```

> `--models sft` 会自动关掉 pairwise（基线不在这一批里），不用另外改配置。
> 这两个数据集都是 `engine="code"`，**整个阶段一次裁判都不调**，裁判服务没起也能跑。

**过关标准**：`out_dir` 下出现这些文件，且 `failure_buckets.csv` 里三个桶加起来正好等于 `1 − pass_rate`：

```
model,dataset,n,pass_rate,fail_malformed,fail_localize_fail,fail_deviation,gt_unparseable_n
sft,ground_box,20,0.6500,0.0500,0.2500,0.0500,0
```

`acceptance_score.csv` 这时候 `total_score` 是空的、`excluded_small_n` 里写着 `ground_box(n=20)` —— **这是对的**，n < 30 不给结论。别当 bug 修。

`warnings.log` 一定要看一眼。最常见的两条：

```
[skip] sft ground_box prediction file not found: ...     ← 路径错了
[warn] ground_box 真值中有 20/20 行没有可用图片          ← image_root 没配对
```

第二条出现就**停下来**：模型没看见图，框出来的全是废的，后面所有数字都没有意义。

## 阶段 2 · 八个主线数据集全量（一两个小时，仍不用裁判）

把 `limit` 删掉，`enabled_datasets` 放开到八个主线（**先不要加后三个派生集**，它们要等阶段 5）：

```json
"enabled_datasets": ["ground_box", "detect_box", "region_identify", "count_class",
                     "inventory", "attribute_qa", "exist_negative"]
```

```bash
python -m eval_tool infer --config det.json --models sft
python -m eval_tool eval  --config det.json --models sft
```

**过关标准**：`acceptance_score.csv` 出数了（各数据集 n 都过 30），`breakdown.csv` 能按 `task_type` / `difficulty` / `size_bucket` / `label` 拆开看。

这时候第一次能回答"画框到底行不行"：

```
达标 = 解析出框 ∧ IoU ≥ 0.5 ∧ 四点平均偏差/scale ≤ 5%
```

不达标看 `failure_buckets.csv` 分三个方向补数据：`malformed` 是训练配置问题、`localize_fail` 补指代消歧和密集场景、`deviation` 补精细边界（再看 `detail_*.xlsx` 里的 `bias_*` 定方向 —— 是系统性画小了还是画偏了）。

## 阶段 3 · 加 D 组描述（第一次要裁判）

`enabled_datasets` 加上 `"describe"`。裁判服务先起好，然后：

```bash
# 先不调裁判，只出三个代码指标 —— 它们本来就是最先该看的
python -c "
import json; d=json.load(open('det.json')); d['do_pointwise']=False
json.dump(d, open('det_nojudge.json','w'), ensure_ascii=False, indent=2)"
python -m eval_tool eval --config det_nojudge.json --models sft
```

`breakdown.csv` 里先看 `scope_ok`（范围合规）、`chair_i` / `chair_s`（幻觉）、`is_filler`（空话）。**范围合规必须走代码** —— 通用的"描述准确性"rubric 会给跑题答案高分（说得没错啊），裁判判不出"跑题"这件事。

三个代码指标看着正常了，再打开裁判跑全量：

```bash
python -m eval_tool infer --config det.json --models sft
python -m eval_tool eval  --config det.json --models sft
```

**过关标准**：`chair_available` 不是整列 0（是的话说明 `labels_dir` 或 `classes_yaml` 没配对，见坑 ①），裁判分和三个代码指标走向一致。**走向不一致时以代码指标为准。**

## 阶段 4 · 交叉裁判（有第二个裁判才做）

手上有异家族裁判（InternVL / MiniCPM，别的家族都行）就配上，`judge` 块里加：

```json
"cross_check": [
  {"name": "internvl", "api_base": "http://127.0.0.1:18181/v1/chat/completions",
   "model": "InternVL2-26B"}
]
```

只写和主裁判不同的字段，其余全继承（提示词一定继承 —— 换了提示词就不是在比裁判，是在比提示词）。不用重推，直接重跑 eval：

```bash
python -m eval_tool eval --config det.json --models sft
```

启动时两行日志确认两路都起来了：

```
[judge] model=qwen3.6-27b fingerprint=e2dfee504ecaf110
[judge:internvl] model=InternVL2-26B fingerprint=bb04c7671e0f864f
```

**过关标准**：`judge_agreement.csv` 出数。先看 `spearman` —— 它低说明两个裁判对"哪条答得好"根本没共识，那么裁判分本身就不可信，D 组结论得往回收。

只有 sft 一个模型时 `judge_conclusion.csv` **不会出**，那是对的：它算的是相对 base 的增益在两个裁判下各是多少，没有 base 就没有增益可比。等阶段 6 跑完 base 它自己就出来了。

## 阶段 5 · 三个派生集

这三个都要**先有主线预测**，所以必须排在阶段 2 之后。派生是纯函数，不用 GPU，秒出。

```bash
# ① 模型历史（链路衰减率）—— 抽 30%
python -m eval_tool derive --mode model-history \
  --eval-set /data/eval/test.jsonl \
  --pred work_dir_det/sft/sft_eval_set_v1.xlsx \
  --sample-ratio 0.3 \
  --out /data/eval/describe_modelhist.jsonl

# ② 双向一致性（正向的框拿来反问「这个框里是什么」）
python -m eval_tool derive --mode reverse-consistency \
  --eval-set /data/eval/test.jsonl \
  --pred work_dir_det/sft/sft_eval_set_v1.xlsx \
  --pool region_identify=/data/builder/prompts/region_identify/region_identify.txt \
  --tasks ground_appearance,ground_full,ground_relation \
  --out /data/eval/reverse_consistency.jsonl

# ③ 问法扰动（同一个目标换 3 种说法）
python -m eval_tool derive --mode question-perturbation \
  --eval-set /data/eval/test.jsonl \
  --pool ground_appearance=/data/builder/prompts/ground_attribute/ground_attribute.txt \
  --variants 3 --sample-ratio 0.15 \
  --out /data/eval/question_perturbation.jsonl
```

派生出来的就是**普通数据集**，`enabled_datasets` 放开后三个，再推一遍、评一遍：

```bash
python -m eval_tool infer --config det.json --models sft
python -m eval_tool eval  --config det.json --models sft
```

**过关标准**：`chain_decay.csv` 出数。读法：

| 现象 | 结论 |
|---|---|
| 衰减大 | 瓶颈在**定位** —— 框错了描述再好也白搭，补定位数据 |
| 衰减小但 `gold_score` 本身低 | 瓶颈在**描述** —— 补描述数据 |
| 两个都高 | 这一轮 SFT 成了 |

## 阶段 6 · base 也跑一遍，出真正的对比

前五个阶段都只跑 sft，回答的是"sft 现在什么水平"。**"SFT 到底涨了多少"必须有 base。**

```bash
python -m eval_tool infer --config det.json          # 不带 --models，两个都跑
python -m eval_tool eval  --config det.json
```

sft 的预测和裁判判词都在缓存里，这一趟只多跑 base 那一半。

**过关标准**，按这个顺序看：

| 文件 | 回答 |
|---|---|
| `acceptance_score.csv` | 验收总分（只由代码打分器构成，不含裁判分） |
| `paired_diff_vs_baseline.csv` | 相对 base 的**配对** bootstrap 差值，`significant` = 区间不含 0 |
| `failure_buckets.csv` | 还差的那部分该往哪个方向补数据 |
| `breakdown.csv` | 哪一档 / 哪一类 / 哪种尺寸还不行 —— **这才是真正的产出** |
| `judge_conclusion.csv` | 换个裁判结论会不会翻。`verdict=flipped` 的那份增益不能报 |
| `run_fingerprint.json` | 这份结果评的是哪一批样本、什么口径、哪个裁判 |

只出一个总分没有用。这套评估设计的全部意义在 `breakdown.csv` 那一张。

## 常见坑

**① `classes_yaml` 不配，E 组主指标会偏高。** 兜底类别表只含评估集里出现过的 label。真值"人员"、模型答"军事人员"，最长匹配会从模型答案里抠出"人员"判成**完全正确** —— 那是白送分。配了会打印一行警告，`class_table_authoritative=0`；同理 CHAIR 会**漏报**幻觉（模型编个"船"，表里没有"船"，那个词根本不会被认成类别）。

**② 像素面积必须和训练配置一致。** `infer.training` 写了就硬校验，不一致直接报错：

```
infer.training 声明了训练时的像素面积，但推理没设 image_min_pixels / image_max_pixels
```

分辨率变了，坐标虽是归一化的不会错位，但模型的空间精度会变，测出来的数字不可比 —— 而这件事**在报表上完全看不出来**，只表现为"这个 checkpoint 好像差一点"。照抄 LLaMAFactory 的配置。

**③ 缓存不要删。** `cache_dir` 下的 `judge_cache_*.jsonl` 是重跑和加模型的全部本钱。缓存键第一位是裁判指纹，换 rubric、换裁判会自动 miss 重判，不会串。

**④ `baseline_model` 必须在 `models` 里。** 想只跑 sft 就用 `--models sft`，别去 `models` 数组里删 base —— 那会直接报 `baseline_model not found in models: base`。

**⑤ 交叉裁判挂了不会带崩主评估。** 只记一条 warning、跳过那一路，主裁判的 `hit` 一个数不变。所以跑完记得扫一眼 `warnings.log`，别把"交叉验证没跑成"当成"结论一致"。

**⑥ 空格子不是 bug。** `breakdown.csv` 里 `status` 为 `by_design`（该组合本就不产样本，如 `ground_part` 没有 hard 档）/ `not_in_data`（该任务产出为 0）/ `insufficient`（n < 30）时百分比都是空的。三种是完全不同的三件事，看到空格先看 `status`。
